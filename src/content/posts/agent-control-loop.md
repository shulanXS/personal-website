给模型一段报错，让它解释原因，通常只需要一次请求。但如果要求它读取仓库、修改代码、执行测试，再根据失败结果继续修复，系统就必须处理一个新的问题：谁来决定下一步，以及什么时候结束？

本文用一个代码修复任务讨论这个问题。这里的 Harness 指包裹模型的执行环境与控制逻辑；不同项目对这个词的边界并不完全一致，本文把工具调度、状态记录、预算和结果验证都算在其中。

## 先判断是否需要 Agent

[Anthropic 对 workflows 与 agents 的区分](https://www.anthropic.com/research/building-effective-agents)是：前者主要沿预设代码路径运行，后者由模型动态决定过程和工具使用。这个区分有助于选型，但不意味着自主程度越高越好。

例如，把 Markdown 转成 HTML，可以直接调用构建工具。即使中间加入模型生成摘要，步骤仍然可以固定。只有当下一步依赖尚未看到的结果，例如测试失败后需要决定查看哪个文件，动态循环才更有价值。

我的设计原则是：把确定的部分留在代码里，把需要根据观察选择的部分交给模型。测试命令、目录权限与最大执行时间，不必由模型每轮重新发明。

## 一轮执行需要哪些信息

以修复失败测试为例，一轮至少涉及四种对象：

| 对象 | 示例 | 负责方 |
| --- | --- | --- |
| 目标 | 修复日期解析，保持现有接口 | 用户与任务配置 |
| 观察 | 文件片段、测试输出、退出码 | 工具执行器 |
| 动作 | 读取文件、应用补丁、运行测试 | 模型提出，执行器校验 |
| 验收证据 | 指定用例通过、补丁范围符合要求 | 独立检查逻辑 |

工具输出应当成为下一轮的观察。模型说“已经修好”只能视为结束请求，不能直接等同于通过验收。

下面是架构伪代码，`model`、`policy` 和 `tools` 代表需要接入的模块，不是某个 SDK 的现成接口：

```python
for step in range(max_steps):
    if deadline_expired():
        return stop("deadline")

    decision = model.decide(goal, observations)
    if decision.kind == "finish":
        evidence = verify_acceptance()
        return finish(evidence)  # 失败时也明确返回失败证据

    policy.validate(decision.action)
    observation = tools.execute(decision.action, timeout=30)
    observations.append(observation)

return stop("step_budget_exhausted")
```

这段伪代码故意没有加入自动重试。对于写文件、提交工单之类的动作，能否重试取决于副作用与幂等设计，不能统一用一个 `except: continue` 解决。

## 预算要覆盖整条执行链

只限制循环次数并不充分。一轮可能执行一个耗时很长的工具，也可能并发触发多个昂贵操作。实际系统可以分别限制模型调用数、工具调用数、墙钟时间和费用。

这些预算需要由 Harness 持有。工具执行器负责超时与子进程清理；调度器负责禁止在截止后启动新步骤；模型收到剩余预算后可以调整策略，但不能自行解除限制。

还要区分“预算耗尽”与“任务失败”。前者表示系统停止继续尝试，未必已经证明任务不可完成。给用户的结果应当包含已完成内容、最后一个有效观察，以及继续工作所缺的条件。

## 怎样检查最小实现

可以先准备三个不调用真实模型的场景，用固定决策序列检查控制逻辑：

1. 模型立即请求结束，但测试失败，结果必须保留失败状态。
2. 模型持续请求读取同一个文件，达到预算后必须停止。
3. 工具卡住或报错，执行器必须回收资源并产生可识别的错误观察。

通过这些检查，只能说明循环的机械边界有效，不能证明模型能够修好代码。后者还需要任务级评测。把这两个层次分开，才能判断问题来自控制程序还是决策质量。
