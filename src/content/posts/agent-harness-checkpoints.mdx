A coding agent can lose its process after changing a file but before recording that change. A support agent can lose a network response after the server has already created a ticket. Both failures interrupt a run, but they require different recovery strategies.

Persisting a conversation is not enough. Recovery needs a protocol for reconciling stored intent with the current state of the environment.

## Define the unit of recovery

[Anthropic's work on long-running harnesses](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents) describes the problem of carrying useful progress across separate sessions. The design below focuses on one part of that problem: making the next worker able to determine what remains unconfirmed.

For a repository task, a checkpoint might contain:

```json
{
  "schema_version": 1,
  "task_id": "repair-date-parser",
  "base_commit": "<full commit hash>",
  "phase": "verifying",
  "pending": ["run acceptance suite"],
  "verification": {
    "command": "python -m unittest discover",
    "exit_code": null,
    "artifact": null
  },
  "external_operations": []
}
```

The `null` result matters. Starting a command is not evidence that it completed. A human-readable summary can explain the checkpoint, but should not replace fields that recovery code needs to interpret unambiguously.

For real jobs, include the active workspace identity, relevant artifact hashes, and the version of the task's acceptance contract. Avoid storing API keys or raw credentials in this record.

## Replace a checkpoint without exposing a half-written file

This standard-library example uses a temporary file in the target directory and then replaces the destination. Save it as `checkpoint.py` and run it with Python 3.11 or later.

```python
import json
import os
import tempfile
from pathlib import Path


def save(path: Path, state: dict) -> None:
    path.parent.mkdir(parents=True, exist_ok=True)
    fd, temporary = tempfile.mkstemp(dir=path.parent, prefix=".pending-")
    try:
        with os.fdopen(fd, "w", encoding="utf-8") as stream:
            json.dump(state, stream, ensure_ascii=False)
            stream.flush()
            os.fsync(stream.fileno())
        os.replace(temporary, path)
    finally:
        if os.path.exists(temporary):
            os.unlink(temporary)


def load(path: Path, task_id: str) -> dict:
    state = json.loads(path.read_text(encoding="utf-8"))
    if state.get("schema_version") != 1:
        raise ValueError("unsupported checkpoint version")
    if state.get("task_id") != task_id:
        raise ValueError("checkpoint belongs to another task")
    return state


if __name__ == "__main__":
    with tempfile.TemporaryDirectory() as directory:
        path = Path(directory) / "checkpoint.json"
        save(path, {"schema_version": 1, "task_id": "demo",
                    "phase": "verifying"})
        assert load(path, "demo")["phase"] == "verifying"
        save(path, {"schema_version": 1, "task_id": "demo",
                    "phase": "complete"})
        assert load(path, "demo")["phase"] == "complete"
    print("checkpoint checks passed")
```

This is a **single-writer** example. It prevents readers from observing an ordinary partial write to the destination on filesystems that support atomic replacement. It does not provide distributed coordination, protect against malicious modification, or establish complete power-loss durability on every filesystem. Stronger durability may require syncing directory metadata; multiple writers need transactional storage or version-checked updates.

Loading also performs only two identity checks. A production implementation should validate the entire schema before using its fields to select files or launch commands. Treat a checkpoint as untrusted input if another principal can modify it.

## The ambiguous side-effect window

Consider this sequence:

1. The worker records an intention to create a ticket.
2. The remote server creates the ticket.
3. The response is lost.
4. The worker restarts and sees no saved ticket identifier.

Blindly repeating step two can create a duplicate. Saving the checkpoint more frequently cannot remove this window, because the remote write and the local checkpoint are not one atomic transaction.

If the remote service supports idempotency keys, persist a stable operation key **before** sending the request. Reuse it during recovery, within the service's documented retention and request-matching rules. Where possible, query by that identity before issuing another write.

A local deduplication table alone cannot prove what an external server did. When the provider offers neither durable deduplication nor result lookup, represent the operation as `outcome_unknown`. Stop automatic repetition and request reconciliation. Calling this state “failed” would incorrectly suggest that no side effect happened.

## Reconcile before resuming model decisions

For a coding task, recovery should inspect the current commit and working tree before trusting the old summary. Someone may have edited the repository while the worker was offline. A checkpoint that says “tests passed” is stale if the tested patch no longer matches the current files.

A practical recovery sequence is:

- Validate the checkpoint and workspace identity.
- Inspect the current diff and stored verification artifacts.
- Resolve outstanding external operations.
- Rerun checks invalidated by environment changes.
- Construct the next task state from confirmed facts.

Do not automatically reset or discard unexpected working-tree changes. Preserve them and make the conflict explicit. Recovery is a reconciliation step, not permission to force the world back into the checkpoint's narrative.

## Test interruptions at boundaries

Inject failures after writing a patch, before recording verification, after a remote request, and before storing its response. Then restart in a new process and inspect both the workspace and the remote test fixture.

The relevant assertions are concrete: no duplicated side effect, no lost patch, no acceptance claim without matching evidence, and no silent overwrite of unrelated work. A graceful-exit test alone cannot demonstrate these properties.

For short read-only jobs, this machinery may be unnecessary. Once a run modifies durable external state or spans multiple workers, however, recovery behavior belongs in the task's correctness model rather than in an informal “resume” prompt.
