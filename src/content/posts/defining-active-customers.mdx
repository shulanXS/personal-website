Ask an analytics assistant how many customers were active in October. Imagine that the growth team expects a number for its engagement dashboard and finance expects a number for its sales report. A person who knows both reports would ask which one is meant. A language model can produce valid SQL immediately, before anybody notices there were two questions. I use a four-row database to make that ambiguity observable.

A Text-to-SQL query can be syntactically valid, execute successfully and still answer a different question from the user's. The difficult input is often the metric definition. “Active customer” could mean any customer with an event or only a customer who purchased. Both interpretations map naturally to the same tables and produce plausible counts.

I represent a metric as an entity, grain, qualifying predicate, time interval and reporting timezone. For *purchasing customers in October 2026 UTC*, the entity is a customer, the grain is distinct customer, the predicate is purchase, and the interval starts at October 1 inclusive and ends at November 1 exclusive. A metric catalog or an explicit clarification can supply that contract. Inferring it solely from available column names leaves an important product decision to the decoder. ## Translate the question into set operations

My intermediate representation is deliberately close to something an analyst could review: take October events, keep purchases, project customer IDs, remove duplicates, count the surviving IDs. Each verb corresponds to one decision. Dropping “keep purchases” admits Ada. Dropping “remove duplicates” gives Bo two votes. Including both endpoints admits Cy at the first instant of November.

This ordering is useful even if a database optimizer chooses a different physical execution plan. It supplies a plain-English specification against which to review generated SQL. For a recurring metric I would give that specification an owner and revision. For a one-off question I would present both plausible counts with their definitions, or ask which definition should drive the report if a downstream job needs exactly one value.

## Verify the aggregation and time boundary

```python
import sqlite3

db = sqlite3.connect(":memory:")
db.execute("create table events(customer text, kind text, stamp text)")
rows = [("Ada", "login", "2026-10-02T12:00:00Z"),
        ("Bo", "purchase", "2026-10-03T09:00:00Z"),
        ("Bo", "purchase", "2026-10-17T09:00:00Z"),
        ("Cy", "purchase", "2026-11-01T00:00:00Z")]
db.executemany("insert into events values (?, ?, ?)", rows)
period = ("2026-10-01T00:00:00Z", "2026-11-01T00:00:00Z")
query = """select count(distinct customer) from events
           where stamp >= ? and stamp < ?"""
any_activity = db.execute(query, period).fetchone()[0]
purchasers = db.execute(query + " and kind = ?", (*period, "purchase")).fetchone()[0]
print(any_activity, purchasers)
# 2 1
```

The result is two customers with any October activity and one purchasing customer. Counting purchase *rows* also gives two because Bo purchased twice. This accidental numerical agreement is why matching a single expected scalar on one warehouse snapshot is a weak execution test.

The fixture compares text timestamps only because their UTC representation and precision are uniform. For a production warehouse I use typed timestamps and convert the two local calendar boundaries to instants. A half-open interval composes with the next reporting period and avoids guessing the last representable timestamp on the final day. A local reporting day can have a different duration across a daylight-saving transition.

### A query can pass today for the wrong reason

Suppose someone writes `COUNT(*)` over October purchases and the test dataset contains one purchase per customer. The wrong query and the right query agree on every row of that snapshot. Adding fifty more customers with one purchase each yields a larger test with exactly the same blind spot. Bo's second purchase is valuable precisely because it breaks that agreement.

Joins introduce a less obvious version of the same problem. If each order can carry several promotion codes, joining orders to promotions before counting can duplicate the order rows. A distinct customer count may still look correct while a neighboring revenue metric doubles. I would inspect the row grain immediately after the join and test the two metrics separately. Marking an entire generated query “verified” on the strength of one scalar hides that distinction.

## Metamorphic tests expose ambiguous semantics

A metamorphic test changes the input data and specifies how the output should respond. Starting from the original fixture each time:

- Duplicate Bo's purchase. The purchase-event count increases, but the distinct-purchaser count stays one.
- Add an October login for Cy. The any-activity count becomes three. The purchase count stays one.
- Move Cy's purchase one second before the upper boundary. The October purchaser count becomes two.

These tests constrain the query's meaning without requiring the generated SQL to match a reference string. They also make a useful review tool: a domain expert can approve the expected changes without reading SQL. For joins, I add a one-to-many dimension record to expose duplicate counting after a join.

A verified example ties an approved question to trusted SQL. It should carry a metric revision and the assumptions needed to reuse it. I show the selected metric and timezone with the answer so a reader can see why a query returning `1` was correct for purchasing customers.

## What the person asking the question should see

For the fixture I would return **1 purchasing customer in October 2026, UTC** and a short explanation: two qualifying purchases belonged to the same customer. A link to the metric definition can carry the predicate, timezone and version without forcing everyone to read SQL. If the user meant engagement, the answer is two customers, and the reason is Ada's sign-in. The correction alters the predicate; it should leave the time window and counting grain intact.

There is a useful review question here even for teams that never show generated SQL. Can the system name a customer whose inclusion changes between two plausible definitions, and explain the change using an actual row? In this fixture that customer is Ada. If the system can produce only a number, a reviewer has very little to challenge. A count accompanied by its definition and one discriminating example gives the conversation somewhere precise to go.
