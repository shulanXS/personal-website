A convincing agent demonstration shows a successful trajectory. An evaluation asks a harder question: which tasks succeed, under what conditions, how often, and at what cost?

That difference matters because an agent can modify its environment, choose its own sequence of tools, and finish with a persuasive explanation even when the requested outcome is incomplete. Evaluating the final paragraph alone ignores most of the system's behavior.

## Write the acceptance contract before the grader

[Anthropic's discussion of agent evaluations](https://www.anthropic.com/research/demystifying-evals-for-ai-agents) provides a useful starting point for thinking about multi-turn systems. The concrete design below is a small repository-repair evaluation, not a reported benchmark result.

Suppose the task is to reject invalid date inputs without changing the public parser interface. The acceptance contract should specify supported inputs, expected errors, the allowed edit scope, and the validation command. Hidden tests can exercise additional examples of that contract; they should not introduce an undisclosed interface requirement.

Separate the observable dimensions:

<ResponsiveTable>

| Dimension | Evidence | Typical failure |
| --- | --- | --- |
| Functional result | Tests owned by the evaluator | Regression on valid input |
| Change scope | Diff against the initial workspace | Unrelated files modified |
| Execution policy | Tool-event log | Unauthorized remote write |
| Delivery quality | Response checked against a rubric | Claimed tests were never run |
| Resource use | Calls, duration, usage records | Task solved beyond the allowed budget |

</ResponsiveTable>

A system that passes the tests after deleting unrelated files should not receive the same outcome as a compliant solution. Keep those dimensions available even if a product ultimately needs one pass/fail decision.

## Implement the result policy independently

Save this standard-library example as `grading.py` and run it with Python 3.11 or later. The fixture values are invented solely to exercise the grader; they are not measurements of a model.

```python
from dataclasses import dataclass
from collections import Counter


@dataclass(frozen=True)
class Trial:
    acceptance_passed: bool
    scope_respected: bool
    unauthorized_write: bool
    infrastructure_error: bool = False


def classify(trial: Trial) -> str:
    if trial.unauthorized_write:
        return "policy_violation"
    if trial.infrastructure_error:
        return "infrastructure_error"
    if not trial.scope_respected:
        return "scope_violation"
    return "passed" if trial.acceptance_passed else "task_failed"


def summarize(trials: list[Trial]) -> dict:
    if not trials:
        raise ValueError("at least one trial is required")
    counts = Counter(classify(trial) for trial in trials)
    return {"trials": len(trials),
            "counts": dict(counts),
            "end_to_end_success": counts["passed"] / len(trials)}


if __name__ == "__main__":
    fixtures = [Trial(True, True, False),
                Trial(True, False, False),
                Trial(False, True, False),
                Trial(False, True, False, True)]
    result = summarize(fixtures)
    assert result["end_to_end_success"] == 0.25
    assert result["counts"]["infrastructure_error"] == 1
    assert classify(Trial(True, True, True, True)) == "policy_violation"
    print("grading checks passed; fixture success rate = 0.25")
```

The precedence is a deliberate policy choice: an observed unauthorized write must not disappear behind an infrastructure failure. The summary includes infrastructure errors in the end-to-end denominator because a user still failed to receive a successful result.

For diagnostic analysis, also retain every raw dimension. If you report an infrastructure-filtered rate, label the exclusion rule and provide its sample count. Quietly dropping inconvenient runs can make a fragile product appear reliable.

The tested agent must not supply its own truth values. Trusted evaluator code should derive them from isolated tests, diffs, and event logs. Where the agent can edit a local test suite, run acceptance tests from an evaluator-controlled source. Otherwise, “passing” can reflect modified checks instead of repaired behavior.

## Repeated trials answer different questions

For a one-shot product, the important unit is a fresh task attempt. For a product that offers several attempts, report performance under that fixed attempt budget, including the extra time and usage.

“At least one success in five attempts” is not interchangeable with “five consecutive successful attempts.” The first describes a search opportunity; the second probes repeatability. Correlated attempts, cached state, and shared workspaces can distort either measurement.

Use clean starting environments for independent trials, record any shared dependencies, and show per-task results. A single aggregate rate can hide a system that performs well on easy tasks and consistently fails an important category.

Small samples require restraint. Four successes in five runs are an observed 80%, not a precise forecast of future reliability. Include the number of tasks, trial count, and uncertainty appropriate to the sampling design. Do not apply a simple independent-trials interpretation when repeated runs share substantial state.

## Inspect failures at the correct boundary

Pin or record the repository revision, model identifier, prompt revision, tool implementation, task budget, and environment. Where a hosted model cannot be fully pinned, record the identifier and execution date so the comparison's limits are visible.

When a run fails, locate the first consequential break: missing dependency, wrong file selection, rejected tool argument, incorrect patch, misleading verification, or premature completion. Save the trajectory and relevant artifacts with secrets redacted. Logs that preserve every credential are not a useful evaluation asset.

Infrastructure failures deserve their own investigation. Replacing a flaky package mirror may improve the end-to-end completion rate without changing the model. That is a valid system improvement, but not evidence of better reasoning.

## Build a regression set without turning it into the whole world

Start with a small set of representative real tasks and explicit acceptance contracts. Add failures that expose a meaningful behavior, then rerun the collection after changing the model, tools, prompt, or harness.

Keep a separate held-out collection that is not used for daily tuning. Repeatedly optimizing against the same tasks can overfit workflow details. Avoid choosing a release candidate by repeatedly inspecting the held-out results and then treating that set as untouched.

For open-ended output such as an explanation, use a rubric with concrete anchors and human calibration. A model judge can scale review, but its score is another measurement with failure modes. Check disagreements, prompt sensitivity, and whether superficial writing style overwhelms correctness.

The goal is not a flattering number. It is an evaluation record that lets another engineer reconstruct what ran, how it was graded, and why a particular change should make the deployed system better.
