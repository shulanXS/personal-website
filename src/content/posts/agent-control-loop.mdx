A model that explains a failing test is answering a question. A system that reads a repository, edits a function, runs the tests, and chooses another action from the result is executing a process. That process needs a control plane even when the model is good at deciding what to do next.

This article develops a small, provider-independent runner. The example deliberately uses deterministic callbacks instead of a model SDK: the purpose is to make control-flow properties testable before introducing probabilistic decisions.

## Decide what should remain deterministic

[Anthropic distinguishes predefined workflows from agents that dynamically direct their process](https://www.anthropic.com/research/building-effective-agents). That distinction is useful when choosing where to introduce model decisions. It does not imply that every step should become autonomous.

Consider repairing a date parser. The model may need to choose which function to inspect after reading a traceback. It does not need authority to choose its own filesystem permissions, remove its time limit, or decide that a failing acceptance test is irrelevant.

In this article, **harness** means the surrounding control plane: tool dispatch, policy enforcement, observations, budgets, and result validation. The term has no single universally enforced boundary. A framework may package these responsibilities differently.

A useful state transition is:

```text
observe -> propose -> authorize -> execute -> record -> observe
                  \-> request completion -> verify -> terminal result
```

The model proposes actions. Code determines whether those actions can execute and whether the terminal result represents verified success.

## A minimal runner you can execute

Save this as `agent_loop.py` and run it with Python 3.11 or later. It requires no API credentials or third-party packages.

```python
from dataclasses import dataclass
from typing import Callable, Literal


@dataclass(frozen=True)
class Decision:
    kind: Literal["tool", "finish"]
    name: str = ""
    argument: str = ""


@dataclass(frozen=True)
class Outcome:
    status: str
    observations: tuple[str, ...]


def run(decide: Callable, execute: Callable, verify: Callable,
        allowed: set[str], max_decisions: int = 4) -> Outcome:
    observations: list[str] = []
    for _ in range(max_decisions):
        decision = decide(tuple(observations))
        if decision.kind == "finish":
            status = "verified" if verify() else "verification_failed"
            return Outcome(status, tuple(observations))
        if decision.kind != "tool" or decision.name not in allowed:
            return Outcome("policy_denied", tuple(observations))
        try:
            result = execute(decision.name, decision.argument)
        except TimeoutError:
            return Outcome("tool_timeout", tuple(observations))
        observations.append(result)
    return Outcome("budget_exhausted", tuple(observations))


if __name__ == "__main__":
    sequence = iter([Decision("tool", "read", "parser.py"),
                     Decision("finish")])
    result = run(lambda _: next(sequence),
                 lambda name, arg: f"{name}: {arg}",
                 lambda: True, {"read"})
    assert result.status == "verified"
    assert result.observations == ("read: parser.py",)
    assert run(lambda _: Decision("finish"), lambda *_: "",
               lambda: False, set()).status == "verification_failed"
    assert run(lambda _: Decision("tool", "delete"), lambda *_: "",
               lambda: True, {"read"}).status == "policy_denied"
    assert run(lambda _: Decision("tool", "read"), lambda *_: "ok",
               lambda: True, {"read"}, 2).status == "budget_exhausted"
    print("runner checks passed")
```

The final line should print `runner checks passed`. These assertions establish properties of the runner, not the competence of an agent model. A callback returning `True` is only a test fixture; a real verifier needs trusted acceptance checks and must report their evidence.

## What this runner intentionally does not solve

The decision budget is precise: at most four calls to `decide` occur by default. It is **not** a wall-clock bound. A callback can block forever. Production adapters need per-request deadlines, cancellation, process cleanup, and an overall deadline checked before starting new work. A timed-out thread that keeps running is not equivalent to a terminated tool process.

The runner also does not interpret arbitrary model output. A provider adapter must parse the response, validate the expected structure, and reject malformed decisions. Tool arguments require their own schema and authorization checks; an allowlisted tool name does not make every argument permissible.

Finally, unexpected exceptions currently propagate. This makes programming errors visible during development. A service boundary should capture them as explicit internal failures with a trace identifier, while preserving diagnostic details in restricted logs.

## Completion is a request, not a fact

Suppose the model writes “all tests pass” after running only a local unit test. The harness should evaluate the actual acceptance contract: perhaps the full suite and a patch-scope check are required. A failed verifier should produce a failure outcome, not a polished success message.

A system can allow another repair attempt after failed verification, but it must charge that attempt to the same task budget. Otherwise, a “verification loop” becomes an unbounded retry mechanism hidden inside a bounded outer loop.

Different terminal outcomes should remain distinct in storage and in the user response. `budget_exhausted` means the system stopped trying; it does not prove the task impossible. `policy_denied` means a proposed action exceeded the permitted boundary. Neither should be silently converted into success or automatically retried.

## Extend the runner in the order failures demand

Start with one worker, a narrow tool set, and reproducible tasks. Record decisions, execution results, and acceptance evidence. Add durable state when interruptions become material, and concurrency only when independent work justifies coordination costs.

For the next layer, see [recovering a run after interruption](/posts/agent-harness-checkpoints/). The central design requirement stays the same: each transition must leave enough evidence to distinguish what the system intended from what actually happened.
