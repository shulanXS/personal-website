一次演示里，Agent 修改了代码，运行了几条命令，最后给出一段清楚的说明。整个过程很流畅，却仍然留下一个问题：如果换个输入、重新运行，或者把任务放到干净环境里，它还能完成吗？

评测的作用，就是把这类问题变成可以重复检查的记录，而不只依赖一次令人印象深刻的输出。

## 从可观察的完成条件开始

[Anthropic 的 Agent 评测文章](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)讨论了多轮执行的评估难度与不同评分方式。本文用一个小型代码修改任务，说明如何把结果检查与过程检查落实到自己的 Harness 中。

例如，要求 Agent 给日期解析器增加非法输入检查，可以先写下以下验收条件：

| 维度 | 完成条件 | 检查方式 |
| --- | --- | --- |
| 功能 | 非法日期被拒绝，合法输入保持兼容 | 外部维护的测试集 |
| 范围 | 只修改允许的源码和测试目录 | 补丁路径检查 |
| 过程 | 没有执行未授权的远端写入 | 工具调用记录 |
| 交付 | 说明改了什么，附测试结果 | 结构检查与人工抽查 |

这些条件必须与任务描述一致。如果测试偷偷要求一个从未指定的文件名，就可能是在测隐藏假设，而不是任务能力。

## 结果评分与过程评分要分开

测试全部通过，但 Agent 同时删除了无关文件，不能算合格交付。反过来，严格遵守范围但没有修复错误，也不能算任务成功。

下面的 Python 示例可直接运行，演示一个保守的二值判定。实际项目还需要生成这些输入，而不是让被测 Agent 自己填写：

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class RunResult:
    acceptance_passed: bool
    scope_respected: bool
    unauthorized_write: bool


def passed(result: RunResult) -> bool:
    return (
        result.acceptance_passed
        and result.scope_respected
        and not result.unauthorized_write
    )


assert passed(RunResult(True, True, False))
assert not passed(RunResult(True, False, False))
assert not passed(RunResult(True, True, True))
```

这类规则适合可以直接检查的事实。表达清晰度、论证质量等开放问题，可以引入人工或模型评分，但要给出具体量表，并检查评分者是否偏爱某种措辞。模型评分也会出错，不应因为输出了数字就被视为客观测量。

## 重复运行时不要只挑最好的一次

如果同一个任务连续运行五次，只成功了一次，“成功过”与“稳定完成”就会给出很不一样的印象。

对于必须一次交付的产品，我会优先报告单次成功率与失败类型。对于允许多次尝试的场景，再报告固定尝试预算下至少一次成功的比例。后者必须把额外成本计算进去，不能与单次尝试结果直接比较。

小样本也容易误导。五次中四次成功的 80%，只是这五次的观察比例，不能直接解释为对未来表现的精确预测。展示每次结果、样本数和任务覆盖范围，比单独展示一个百分比更有帮助。

## Harness 自己也可能制造失败

运行前应记录代码版本、模型标识、提示词版本、工具版本、预算和环境。每轮任务使用独立工作区；数据库、缓存和外部服务也要按测试设计隔离或重置。

如果依赖下载失败、测试服务没有启动，应该记录环境错误。它影响用户最终能否完成任务，但在分析模型能力时，需要与推理或代码修改错误分开。否则更换网络环境就可能被误判为模型能力提升。

## 从失败样本建立回归集

一个务实的起点是：先收集少量真实任务，写清验收条件，保存完整执行轨迹。每发现一种有代表性的失败，就补充对应场景；修复 Harness 后，重跑旧场景，检查是否引入回归。

也要保留未用于日常调参的任务。反复针对同一批样本优化，可能只是让系统学会通过那批检查。本文的代码只验证判定规则，不代表某个 Agent 已达到任何实际成功率；真正的结论必须来自可复查的任务运行。

可以结合[工具契约](/posts/agent-tool-contracts/)与[控制循环](/posts/agent-control-loop/)一起设计评测：先明确系统允许做什么，再检查它是否在约束内完成了目标。
